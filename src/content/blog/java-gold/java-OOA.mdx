# 啥是Java OOA

OOA就是面向对象设计和编程，先来看考纲，Java Gold主要考察以下几个部分：

- 声明并实例化 Java 对象（包括嵌套类对象），并解释对象生命周期（包括创建、引用重新赋值和垃圾回收）。
- 创建类和记录类 (`record`)，定义并使用实例字段和静态字段、方法、构造函数，以及实例初始化块和静态初始化块。
- 实现方法重载（Overloading），包括可变参数（var-arg）方法。
- 理解变量作用域，使用局部变量类型推断 (`var`)，应用封装原则，并使对象不可变（Immutable）。
- 实现继承，包括抽象类 (`abstract`) 和密封类 (`sealed`)。重写 (`Override`) 方法，包括 `Object` 类的方法。实现多态，区分对象类型与引用类型。执行类型转换，使用 `instanceof` 运算符和模式匹配（Pattern Matching）来识别对象类型。
- 创建并使用接口，识别函数式接口，并利用接口的 `private`、`static` 和 `default` 方法。
- 创建并使用包含字段、方法和构造函数的枚举 (`enum`)。

但实际上这里有很多司马的细节是平时不会用的，考试会出很司马的写法来考细节，我们概括几个方面。

# 常见的几个问题

## 初始化和各种代码块

假如我们初始化一个类，首先要进行类加载，然后再创建实例。也就说，首先JVM把“图纸”实例化，然后根据图纸创建一个实体。

那么问题就在于什么能触发类加载，这是关键的：

- new 一个对象时
- 访问类的 static 变量 (非 Final)
- 调用类的 static 方法
- 使用反射 (Reflection)
- 初始化子类时，父类会被“连坐”
- 虚拟机启动时的“启动类” (Main Class)

但是当混合了静态代码块和实例代码块（虽然这些b用没有）时，会觉得混乱，看个例子：

```java title="Parent and Child"
class Parent {
    // 1. 父类静态
    static { System.out.println("A: Parent Static"); }
    
    // 3. 父类实例
    { System.out.println("B: Parent Instance"); }
    
    // 4. 父类构造
    Parent() { System.out.println("C: Parent Constructor"); }
}

class Child extends Parent {
    // 2. 子类静态
    static { System.out.println("D: Child Static"); }
    
    // 5. 子类实例
    { System.out.println("E: Child Instance"); }
    
    // 6. 子类构造
    Child() { System.out.println("F: Child Constructor"); }
}

public class Test {
    public static void main(String[] args) {
        System.out.println("--- 第一次 new ---");
        new Child();
        
        System.out.println("\n--- 第二次 new ---");
        new Child();
    }
}
```

静态块会在类加载阶段就执行，想象一下，我们必须先将“图纸”看一遍。所以首先是父类的类加载，然后是子类的类加载。

接着`实例化之前` 会执行实例代码块，然后再实例化，这两个步骤对于一个类是紧接着完成的。在 JVM 眼里，实例代码块的代码会被“拷贝”到构造函数的 super() 之后、构造函数代码体之前执行。

那么其实就是父类实例代码块-父类实例化，然后子类同理。

所以完整的输出就是：

```
--- 第一次 new ---

A: Parent Static (先加载父类)

D: Child Static (再加载子类)

B: Parent Instance (开始初始化父类对象)

C: Parent Constructor

E: Child Instance (父类好了，开始初始化子类对象)

F: Child Constructor

--- 第二次 new --- (注意：静态块不再执行！)

B: Parent Instance

C: Parent Constructor

E: Child Instance

F: Child Constructor
```

还有需要注意的是，假如我们想对于一个类连续创建两个实例化对象，其中的静态代码块会执行两次吗？显然是不会的，因为类加载只会在第一次new对象时才执行，就算你使用反射，只要不用不同的ClassLoader，是不会重新加载这个类的。

下面这个代码可以强制触发二次类加载：

```java title="二次类加载"
import java.net.URL;
import java.net.URLClassLoader;

class MyTest {
    // 这是一个静态块，正常情况下只打印一次
    static {
        System.out.println("🔥 静态块执行了！类被加载了！");
    }
}

public class DoubleLoadTest {
    public static void main(String[] args) throws Exception {
        // 1. 获取当前类路径
        URL url = DoubleLoadTest.class.getProtectionDomain().getCodeSource().getLocation();

        // 2. 创建【加载器 A】
        ClassLoader loaderA = new URLClassLoader(new URL[]{url}, null); // parent设为null以强制自己加载
        Class<?> classA = loaderA.loadClass("MyTest");
        // 触发初始化
        classA.newInstance(); 

        System.out.println("--- 分割线 ---");

        // 3. 创建【加载器 B】
        ClassLoader loaderB = new URLClassLoader(new URL[]{url}, null);
        Class<?> classB = loaderB.loadClass("MyTest");
        // 再次触发初始化
        classB.newInstance(); 
        
        // 4. 验证它们是不是同一个类
        System.out.println("classA == classB ? " + (classA == classB));
    }
}
```

我们使用了两个不同的ClassLoader对象强制触发了类加载。其实这个技术叫`热部署`，它会用在一些需要调试的场景，比如使用Springboot开发时，一修改后端就要重启着实司马，但是伟大的Spring Boot DevTools和Tomcat就会解决这个问题，它们内部就使用了这个机制。

接着我们看看第二条，为什么故意强调了非final呢？如果是一个`static final`的变量，实际上这就是个常量。

```java
class Constant {
    static final String MSG = "Hello";
    static { System.out.println("Static Block"); }
}

// 调用代码：
System.out.println(Constant.MSG);
```
这样做不会触发类加载，因为 `MSG` 是常量，编译器在编译阶段就把它偷偷“宏替换”到了 `Main` 类的常量池里。运行时 `Main` 类其实根本没理会 `Constant` 类。

然后我们看最傻逼的，`通过子类引用父类的静态变量`。

```java
class Super { 
    static int value = 123; 
    static { System.out.println("Super Init"); } 
}
class Sub extends Super { 
    static { System.out.println("Sub Init"); } 
}

// 调用代码：
System.out.println(Sub.value);
```
为什么这样做不会触发子类的类加载呢？实际上这叫做`懒加载`，虽然一个智力正常的人类会直接写`Super.value`，但是你用子类去这样写没任何问题。编译器非常聪明地看到实际上你根本没用子类的任何东西，也就无需加载子类了。

然后是定义数组引用：

```java
Student[] students = new Student[10];
```
这当然不会触发类加载，因为压根就没建对象，里面都是null，其他的什么ArrayList也是一样的道理。

其实最容易混淆的就是`成员变量`这里，因为静态的我们都清楚它是和类直接绑定的，所以我们只看左边就行，但是成员变量竟然也是静态绑定的。

所以`Java的多态，是非静态方法的多态`

看一个纯唐例子：

```java
class Baap {
    public int h = 4;

    public int getH() {
        System.out.println("Baap " + h);
        return h;
    }
}

public class Beta extends Baap {
    public int h = 44;

    @Override
    public int getH() {
        System.out.println("Beta " + h);
        return h;
    }

    public static void main(String[] args) {
        Baap b = new Beta();
        System.out.println(b.h + " " + b.getH());
        Beta bb = (Beta) b;
        System.out.println(bb.h + " " + bb.getH());
    }
}
```

首先`b` 声明类型为 Baap，实际对象为 Beta，那访问属性看左边但调用方法看右边，所以`b.getH()`的返回值就是Beta类内部的h的值，就是44

```
Beta 44 
4 44 
```

接着他强转了类型，换言之声明类型为 Beta，实际对象为 Beta，那这就好办了

```
Beta 44 
44 44
```

这个例子就很好说明了刚才表格写的。

接着我们来看一个例子：

```java
class Super {
    public int num = 10;
    public void run() { System.out.println("Super Run"); }
    public static void fly() { System.out.println("Super Fly"); }
}

class Sub extends Super {
    public int num = 20;
    public void run() { System.out.println("Sub Run"); }
    public static void fly() { System.out.println("Sub Fly"); }
}

public class Exam {
    public static void main(String[] args) {
        Super s = new Sub(); // 【核心】左边 Super，右边 Sub
        
        
        System.out.println(s.num); 
        s.run();
        // !!
        s.fly();
    }
}
```

我们试图用对象调用一个静态方法，虽然这是一种脑瘫写法，因为这等价于`Super.fly()`，但是我们还是要说一句：`静态方法是不参与多态的`。

最后是关于`重载 (Overloading) 的绑定时机`，这个容易出错：

```java
class Tester {
    void test(Animal a) { System.out.println("测试动物"); }
    void test(Dog d)    { System.out.println("测试狗"); }
}

Animal a = new Dog(); // 左边 Animal，右边 Dog
Tester t = new Tester();

t.test(a);
```

必须强调，`重载是静态绑定`。那么就根据之前那个表格我们就知道了，看左边。

test(a)尽管对象是Dog类，但是声明是Animal类的，所以参数类型就是Animal类型，输出必然是：

```
测试动物！
```

总结一下：

在做 OOA 题目时，看到 Parent p = new Child();，脑子里立刻要浮现出三行字：

- 方法调用： 它是谁？(看 new 出来的对象)

- 变量访问： 它的引用类型是什么？(看定义的类型)

- 静态方法： 它的引用类型是什么？(看定义的类型)

只有普通方法是“特立独行”的，其他全是看引用类型。

## 重写三定律 (Overriding Rules)

重写就是子类试图修改父类里已经存在的方法，当你看到打上@Override注解的时候，多半就是这种情况了。

### 定律一：三同 (Signature & Return) —— 身份核查

这里得介绍重载(Overload)的概念，重载其实就是一个类内部的同名但是参数列表不相同的几个方法之间形成的关系，这非常常见，比如构造方法的重载。

- 方法名相同。

- 参数列表相同（类型、个数、顺序完全一样）。

⚠️ 陷阱： 如果参数列表变了一点点（比如 int 变 long），那就不是重写了，那是重载！那是两个无关的方法。

- 返回类型相同（或更小） —— Covariant Return Type (协变返回类型)。

Java 5 之前的古板规则： 必须完全一模一样。

现在的规则： `子类方法的返回值，可以是父类返回值的子类。`

```java
class Parent {
    // 父类返回 Number
    Number getValue() { return 10; }
}

class Child extends Parent {
    // ✅ 正确！Integer 是 Number 的子类 (更小/更具体)
    @Override
    Integer getValue() { return 20; }

    // ❌ 错误！Object 是 Number 的父类 (太大/太宽泛)
    // @Override
    // Object getValue() { return "Error"; } 
}
```
### 定律二：两小 (Exceptions) —— 风险控制

这个是经常注意不到的：

- 抛出的 Checked Exception 范围变小（或相同）。

子类可以抛出父类异常的子类。

子类可以不抛出任何异常。

❌ 绝对不能抛出父类没声明的、更宽泛的 Checked Exception。

- 抛出的 Checked Exception 个数变少。

⚠️ 核心特例（考试必考）：RuntimeException 不受限制！

如果是 NullPointerException, IllegalArgumentException 这种运行时异常，子类爱怎么抛怎么抛，编译器根本不管。

规则只限制 Checked Exception (如 IOException, SQLException)。

```java
class Parent {
    void work() throws IOException { } // 声明会有 IO 风险
}

class Child extends Parent {
    // ✅ 情况1：抛出子异常 (FileNotFound 是 IO 的子类)
    @Override
    void work() throws FileNotFoundException { }

    // ✅ 情况2：什么都不抛 (我很安全)
    @Override
    void work() { }

    // ✅ 情况3：抛出运行时异常 (编译器不管)
    @Override
    void work() throws NullPointerException { }

    // ❌ 情况4：抛出更大异常 (Exception 是 IO 的父类) -> 编译错误！
    // @Override
    // void work() throws Exception { }
}
```

你可能觉得，为啥要子类抛的异常要是父类异常的子类？子类弄个更大的异常兜底不好吗？

因为要满足Liskov 替换原则 (Liskov Substitution Principle, LSP) 是面向对象设计原则 (SOLID) 中最重要、也最容易被误解的一个。

简单用一句话概括就是： “凡是父类对象出现的地方，都能用子类对象替换，而且程序不会出错。”

听起来像是废话？但实际上，Java 的重写规则（三同、两小、一大）全都是为了维护这个原则而存在的。

假设你用更大的异常兜底，那么想想看，父类出现的地方还能不能用子类出现？

### 定律三：一大 (Access Modifiers) —— 门户开放

保证“父类能去的地方，子类也能去”。

- 访问权限必须变大（或相同）。排序： public > protected > package-private (默认) > private。

如果父类是 protected，子类只能是 protected 或 public。如果父类是 public，子类只能是 public（不能退步）。

然后也是我们刚才聊过的：

接口方法： 默认是 public abstract。

实现类： 必须显式加上 public。

如果你忘了写修饰符，它就变成了 package-private，权限变小了 $\rightarrow$ 编译错误。

```java
class Parent {
    protected void sleep() { }
}

class Child extends Parent {
    // ✅ 变大 (Public > Protected)
    @Override
    public void sleep() { }

    // ❌ 变小 (Default < Protected)
    // @Override
    // void sleep() { } 
}
```
所以咱们总结一下：

final 方法： 官方禁止修改。

static 方法： 属于类，不属于对象。（子类同名方法叫“隐藏”）。

private 方法： 子类根本看不见，无法重写。（子类同名方法是“新定义的方法”）。


## 抽象与接口的博弈 (Abstract vs Interface)

### 我们必须先理解他俩的区别

抽象类，只不过就是一个无法直接实例化的类，他必须通过其他类的继承去实现内部的`抽象方法`，神奇的是`它有构造方法`，因为这是给他子类提供的。

但是你懂的，囿于他类的身份限制，子类只能继承他一个，他自己也只能有一个父类，这就意味着扩展性没接口好。最重要的`可以有实例变量和实例方法`。

接口是个神奇的东西，它无法实例化，也没构造方法，更没成员变量。他支持多实现，一旦一个类实现某个接口，就必须实现接口内部所有的抽象方法。

如果内部有变量声明，那它一定是个常量（static final）的。

Java 8以后，接口内可以有静态方法，并且在接口里增加了`默认方法`，下面会说到他怎么用。

Java 9之后，接口内部的方法可以是private的。

接下来我们介绍几个坑。

### 默认（缺省）的权限区分

方法权限的default，也就是缺省，是因方法的种类而异的。我们需要注意：

```java
class Person {
    String name; // 没写 public，也没写 private -> 这就是 Default 权限
    
    void run() { } // 同上
}
```

如果是一般的实例方法，缺省其实就是package-private，就是我们最熟悉的那个Default权限。

```java
interface Runner {
    // 这里的 default 不是权限！它代表“默认实现”！
    default void run() { 
        System.out.println("跑");
    }

    void stop();
}
```
默认方法不写权限，默认它是public的。而普通的接口内部的方法，是public abstract的

所以我们刚才为什么提这个接口的权限问题，看下面这个：

```java
// 1. 定义接口
interface Animal {
    void eat(); 
}

// 2. 实现类
class Dog implements Animal {
    
    void eat() { 
        System.out.println("狗吃肉");
    }
}
```

接口内部必然是public的，但是你实现的方法居然是default，也就是package-private的，这样就会报错。

### 抽象类的“假”构造函数

刚才我们说，抽象类的构造函数其实就是个摆设，他是为了给将来的子类继承用的。

```java
abstract class Base {
    Base() { System.out.println("Base"); }
}

// 问：下面哪行代码能编译？
// A. Base b = new Base();
// B. Base b = new Sub(); // Sub 是具体子类
```

肯定是B能编译，我们可以利用多态去构建子类对象让一个父类引用接收，哪怕父类是个抽象类，这和接口的道理类似。

### 矛盾的修饰符

到这我们捋一捋修饰符abstract。各种权限和各种特性的修饰符，有些不能共存，从逻辑上就能简单地理解。

1. abstract final ： abstract意味着没有方法体需要子类给我重写，而final意味着禁止重写，这当然不行。
2. abstract static：static意味着我这个方法应该是和类绑定的，按照逻辑上来说必须有方法体，因为我无需实例化就能通过类名调用静态方法，而它没有方法体，这就是矛盾的。
3. abstract private：这更好理解，如果你的方法对于子类都不可见，那还重写个锤子啊，所以这也不行。

所以，abstract修饰方法只能和public和protected搭配。

### 最出生的--默认方法冲突 (Diamond Problem)

```java
interface A { default void run() {} }
interface B { default void run() {} }

class C implements A, B { } 
```

不是默认方法压根就不用实现类重写吗？但是这就出问题了，一个类C实现的两个接口A和B里的默认方法run长得一毛一样，编译器就懵逼了，所以这种情况必须重写。

### 欠债还钱

接口以及抽象类内的抽象方法你可以认为是一种承诺，终有一天它们必须被实现，但是如果出现了多继承、多实现的情况会怎么样？

```java
interface I { void work(); }

// 1. 抽象类 A 实现 I，但没写 work()
abstract class A implements I { } // ✅ 编译通过（它也是老赖）

// 2. 抽象类 B 继承 A
abstract class B extends A { }    // ✅ 编译通过（继续传给下一代）

// 3. 实体类 C 继承 B
class C extends B { }             // ❌ 编译错误！
```
所以最终这个欠债的C必须偿还之前所有的债务。

### 这些东西存在的意义

接下来说说为什么要搞这些默认方法之类的东西。

首先来说说抽象类，它与一个设计模式紧密联系：`模板方法模式 (Template Method Pattern)`

抽象父类定义好工作流程，让子类去具体拓展实现，举个例子：

```java
// 【抽象类】：定义模板
abstract class Worker {

    // 1. 【模板方法】 (Template Method)
    public final void dailyRoutine() {
        getUp();
        commute(); // 抽象的，由子类决定怎么去
        work();    // 抽象的，由子类决定干什么
        goHome();
    }

    // 【具体方法】：通用的步骤，父类直接写死
    private void getUp() {
        System.out.println("闹钟响了，起床洗漱");
    }

    private void goHome() {
        System.out.println("下班回家，躺平");
    }

    // 【抽象方法】：留给子类填空的“坑”
    protected abstract void commute();
    protected abstract void work();
}

// 【子类 A】：程序员
class Programmer extends Worker {
    @Override
    protected void commute() { System.out.println("坐地铁去公司"); }
    
    @Override
    protected void work() { System.out.println("写 Java 代码"); }
}

// 【子类 B】：老板
class Boss extends Worker {
    @Override
    protected void commute() { System.out.println("开豪车去公司"); }
    
    @Override
    protected void work() { System.out.println("给员工画饼"); }
}

// 【测试】
public class Test {
    public static void main(String[] args) {
        Worker w1 = new Programmer();
        w1.dailyRoutine(); // 跑一套标准流程
        
        System.out.println("---");
        
        Worker w2 = new Boss();
        w2.dailyRoutine(); // 流程一样，细节不同
    }
}
```
抽象类`dailyRoutine`这个方法，内部安排好了一套方法执行的流程。核心要点是他加了 final关键字。因为这是 SOP，不允许子类瞎改流程顺序。

两个方法getUp、goHome由于是通用的步骤，也就是说无论子类咋样都这么执行，所以写死在父类里，通过private权限阻止传递。

剩下的交给子类实现。

你发现Programmer和Boss的实现完全不一样，所以这样我们其实就完成了一套模板和两个具体实现。

然后来说说默认方法，默认方法是Java 8之后提出的。为啥要有这种东西？

首先它`能调用接口内部的抽象方法`。这个属实牛逼，因为反正这之后你也得找个实现类实现这个方法，我可以参照模板方法模式的思路去无痛拓展接口功能。

比如我们看看：

```java
public interface Iterator<E> {
    boolean hasNext();
    E next();

    // 【实锤】这里用了 default！
    default void remove() {
        throw new UnsupportedOperationException("remove");
    }

    // 【实锤】forEachRemaining 也是 default 的
    default void forEachRemaining(Consumer<? super E> action) { ... }
}
```
用迭代器访问集合时，移除其中的元素是不安全的，所以你调用remove就会报错。

但是我现在实现一个接口，但我完全不想内部的所有方法，因为很多方法吊用没有。比如

```java
interface GymMember {
    void run();          // 跑步
    void swim();         // 游泳
    void liftWeights();  // 举重
    void yoga();         // 瑜伽
    void boxing();       // 拳击
}

```

哥们儿想运动，但是它只跑步：

```java
class ZhangSan implements GymMember {
    public void run() { System.out.println("我就想跑个步..."); }
    
    // 下面全是垃圾代码，但不写编译不过！
    public void swim() {} 
    public void liftWeights() {}
    public void yoga() {}
    public void boxing() {}
}
```
张三累死了，写了一堆废话代码。

这时候就要用到另一个模式，也就是`缺省适配器模式 (Default Adapter Pattern)`。

传统的方法是，用抽象类过桥，你可能觉得这就是把史藏了起来：

```java
// 这是一个抽象类，它把活儿都揽下来了，但都是敷衍了事（空实现）
abstract class GymAdapter implements GymMember {
    public void run() {}
    public void swim() {}
    public void liftWeights() {}
    public void yoga() {}
    public void boxing() {}
}

class ZhangSan extends GymAdapter {
    // 只需要重写这一项！其他的都自动用父类的空实现。
    @Override
    public void run() {
        System.out.println("爽！只写我关心的代码。");
    }
}
```

这样就没毛病了。

但是既然现在有了伟大的默认方法你就可以：

```java
interface GymMember {
    // 默认全是空的
    default void run() {}
    default void swim() {}
    default void liftWeights() {}
    default void yoga() {}
    default void boxing() {}
}

class ZhangSan implements GymMember{
    // 只需要重写这一项！其他的都自动用父类的空实现。
    @Override
    public void run() {
        System.out.println("爽！只写我关心的代码。");
    }
}
```

这是不是就非常合理了呢，所以默认方法，一能扩展老接口（史）的功能，二能选择性地让实现类重写方法，真的是大大滴好。

## 嵌套类 (Nested Classes)

这是最狗史的、最出生的一部分。嵌套类有以下几种：

1. 静态嵌套类
2. 成员内部类
3. 局部内部类
4. 匿名内部类

### 静态嵌套类 (Static Nested Class)

这是纯骗人玩的，因为它其实和外部类是平级关系：

```java
class Outer {
    static String staticStr = "外部静态";
    String instanceStr = "外部实例";

    // 【静态嵌套类】
    static class Roommate {
        void test() {
            // ✅ 可以访问外部类的 static 变量
            System.out.println(staticStr); 
            
            // ❌ 编译错误！不能访问外部类的实例变量
            // System.out.println(instanceStr); 
        }
    }
}

public class Test {
    public static void main(String[] args) {
        // 【考点】实例化语法：
        // 不需要先 new Outer()，直接 new Outer.Roommate()
        Outer.Roommate r = new Outer.Roommate(); 
    }
}
```
当然它有一个小特权就是，它内部无需去通过外部类的`类名.变量`的形式，换言之`Outer.staticStr`的形式去访问（当然想写也行）。

它的实例化也无需外部类的实例对象，就像这段代码做的。

### 成员内部类 (Member Inner Class)

这种是最需要注意的，也是最恶心的。

```java
class Outer {
    private String name = "宿主";

    // 【成员内部类】
    class Parasite {
        void eat() {
            // ✅ 随便访问，Private 也不在话下
            System.out.println("吃掉：" + name); 
        }
    }
}

public class Test {
    public static void main(String[] args) {
        // 1. 先要有宿主
        Outer host = new Outer();
        
        // 2. 【考点】变态的实例化语法：
        // 必须用 宿主对象.new 内部类()
        Outer.Parasite p = host.new Parasite();
        
        // 或者一行写完：
        // Outer.Parasite p2 = new Outer().new Parasite();
    }
}
```

必须要有外部类的对象，你才能实例化内部类，必须用 宿主对象.new 内部类()这个形式去实例化。

所以成员内部类可以随意地访问外部类的任何内容。

这里要注意this

```java
class Outer {
    int x = 100; // 外部类的 x

    class Inner {
        int x = 200; // 内部类的 x

        void print() {
            int x = 300; // 局部变量 x
            
            System.out.println(x);            // 输出 300 (就近原则)
            System.out.println(this.x);       // 输出 200 (内部类的成员)
            System.out.println(Outer.this.x); // 输出 100 (外部类的成员) -> 【必考】
        }
    }
}
```
内部类如何访问外部的成员变量？Outer.this

### 局部内部类 (Local Inner Class)

这个出现在方法内部，临时搭建的一个实例类。

```java

class Outer {
    void method() {
        int wage = 100; // 局部变量
        // wage = 200; // ❌ 如果后面改了它，内部类就不能用了！

        // 【局部内部类】
        class TempWorker {
            void work() {
                // ✅ 可以访问 wage，因为 wage 没变过（Effectively Final）
                System.out.println("拿钱：" + wage);
            }
        }
        
        new TempWorker().work();
    }
}
```

它想用方法里的局部变量，那个变量必须是 final 或者 “事实上是 final (Effectively Final)” 的。

### 匿名内部类 (Anonymous Inner Class)
```java
interface Button {
    void click();
}

public class Test {
    public static void main(String[] args) {
        // 【匿名内部类】
        // 这里的 new Button() 其实是 new 了一个“实现了 Button 的无名类”
        Button b = new Button() {
            @Override
            public void click() {
                System.out.println("点击！");
            }
        };
        
        b.click();
    }
}
```
这是最具有使用价值的，虽然已经被lambda表达式取代了。

你经常能在new接口的时候发现这个实质上的匿名内部类。

# 新特性

## var关键字(Java 10)

这是一个语法糖，官方给它的作用起的名叫：`局部变量类型推断 (Local Variable Type Inference)`。你从这个名也能看出来，它实际上是用来简化局部变量声明的。
有些变量，尤其是集合类+一堆泛型，属实会在左边增大一堆没用的代码，所以当能一眼看出变量声明的类型时，就可以用这个关键字替代了。

```java
public void method() {
    // 1. 基本数据类型
    var age = 18;           // 推断为 int
    var money = 100.5;      // 推断为 double
    
    // 2. 引用类型
    var name = "Java";      // 推断为 String
    
    // 3. 最爽的时刻：简化啰嗦的泛型
    // 以前：HashMap<String, List<Integer>> map = new HashMap<String, List<Integer>>();
    // 现在：
    var map = new HashMap<String, List<Integer>>(); // 推断为 HashMap
    
    // 4. 用在 for 循环里
    for (var i = 0; i < 10; i++) { }
    for (var entry : map.entrySet()) { }
}
```
尤其是上面那个HashMap，是不是很好用。

但是要注意，以下几个情况不能使用var关键字：

1.  成员变量
2.  方法参数
3.  方法返回值
4.  只声明不初始化
5.  数组初始化器
6.  Lambda 表达式直接赋值
7.  赋值为 null
   
首先，成员变量、方法参数和方法返回值类型非常好理解，因为这需要你显式声明而你直接省略那是不行的。局部变量只声明不初始化、赋值null也是同样的问题，光是null不知道具体究竟是什么类型的。

数组初始化器的例子，比方说：

```java
int[] arr1 = {1, 2, 3}; // ✅ 传统写法可以
var arr2 = {1, 2, 3};   // ❌ 编译错误！编译器推断不出这是 int[]
var arr3 = new int[]{1, 2, 3}; // ✅ 必须加上 new int[] 明确类型
```

Lambda表达式主要问题在接口的多实现上：

```java
Runnable r = () -> {}; // ✅ 知道是 Runnable
var f = () -> {};      // ❌ 编译器懵了：这是 Runnable? 还是 Callable? 还是自定义接口?
```


## Record 关键字(Java 17)

它的主要作用是简化`数据载体类`的定义，啥叫数据载体呢：

```java
public class Point {
    private final int x;
    private final int y;

    public Point(int x, int y) {
        this.x = x;
        this.y = y;
    }

    public int getX() { return x; }
    public int getY() { return y; }

    // 还要写 equals, hashCode, toString... 省略 50 行代码
}
```

比如说我想要定义这种二维坐标类，内部的坐标一旦赋值就不改。

如果我像传统pojo类一样还写一坨，那属实是有点浪费。因为这种类的参数实际上都不可变，只是一个暂时存储的作用，所以：

```java
    // 一行搞定！
public record Point(int x, int y) {}
```

这里面包含了啥呢？
 - 私有、Final 的字段
 - 全参构造函数
 - 访问方法，也就是getter，但是和POJO累的命名不一样。比如上面这个就是x() 和 y()。
 - equals() 和 hashCode()，基于内容比较
 - toString()方法

接下来是它的一些规则：
  - 禁止 extends 其他类：Record 隐式继承自 java.lang.Record。Java 是单继承的，所以它不能再继承别的类了。但是： 它可以实现接口 (implements Runnable)。
  - 禁止被继承 (Final)：Record 类默认是 final 的。你不能写 class MyRecord extends Point。
  - 禁止定义“实例字段” (Instance Fields)：除了头部声明的 (int x, int y)，你不能在花括号 {} 里再定义 private int z;。但是： 你可以定义 静态字段 (static int count;)。
  - 禁止定义“空参构造” (除非你自己手写)：它默认只有全参构造。如果你想要 new Point()，必须自己手动写一个无参构造器，并在里面调用 this(0, 0)。
  - 字段全是 Final 的：一旦创建，不能修改！没有 Setter 方法！point.x = 10; $\rightarrow$ ❌ 编译错误。
  - 访问器方法名字没 get：调用 point.getX() $\rightarrow$ ❌ 编译错误（除非你自己额外写了一个 getX() 包装一下）。

它还有一个小技巧，比如说当我想在创建对象时校验变量：
```java

public record Point(int x, int y) {
    public Point {
        // 1. 做校验
        if (x < 0) {
            throw new IllegalArgumentException("x不能小于0");
        }
        
        // 2. 做数据处理（可以直接修改参数）
        if (y < 0) {
            y = 0; 
        }
        
        // ⚠️ 注意：最后绝对不要写 this.name = name;
        // 编译器会在代码最后自动帮你加上赋值语句！
    }
}
```

更高级的操作，比方说我想弄一个嵌套内部Record，这样它就可以是private的：

```java
public class OrderService {

    // ✅ 合法！
    // 这是一个私有的内部 Record，只有 OrderService 能用它
    private record OrderItem(String id, int count) {}

    public void process() {
        // 自己内部随便用
        OrderItem item = new OrderItem("A100", 5);
    }
}
```
但是这样定义的record是一个：`隐式静态的`。这就意味着Record 内部不能直接访问外部类的非静态成员。
这里需要小小注意。

## sealed permits关键字(Java 17)

要定义密封类，需要两步走：

1. 父类声明： 使用 sealed 开启封锁，使用 permits 指定白名单。

2. 子类回应： 子类必须明确表态，如何处理这个继承权。

首先声明父类，比如这是一个形状类：

```java
// 【父类】：我是密封的，我只允许 Circle, Square, Rectangle 三个人继承我
public sealed class Shape permits Circle, Square, Rectangle {

}
```
这时候子类的处理有三种：
1. final，不能被继承
```java
final class Circle extends Shape {}
```

2. sealed，接下来还有指定的子类继承
```java
sealed class Square extends Shape permits ColorSquare {}
final class ColorSquare extends Square {}
```
3. non-sealed，接下来随便被继承
```java
    non-sealed class Rectangle extends Shape {}
    class FancyRectangle extends Rectangle {}
```
   

接下来是需要注意的：

1. 被 permits 的子类，必须和父类在同一个包里
2. 匿名内部类禁止，密封类不能有匿名子类，因为名单内没有
3. Record 与 Sealed 的配合，Record是天然final的，非常适合。
4. Permits 可省略的情况：如果父类和所有子类都写在同一个 .java 文件里，permits 可以省略，编译器会自动识别。

其中第一个是最重要的，被 permits 的子类，必须和父类在同一个包里，严守。

这东西经常用于搭配switch case语句。根据它的特点，什么情况下可以使用呢：

1. “我知道所有可能的子类”： 比如支付状态、用户等级、API 响应结果。

2. “这些子类的内部数据结构不一样”： 比如成功的包很大，失败的包很小。防止胡乱继承出现问题。
   
比如：表达式树 / 语法树 (AST) —— 计算器或解析器

这是计算机科学中最经典的应用，这种语言属于上下文无关文法（CFG）。当你需要解析一个数学公式（如 1 + 2 * 3）时，公式的结构是递归的，且类型是固定的。

结构定义： 一个表达式 (Expr) 只能是以下三种情况之一：

- 一个具体的数字 (Num)

- 加法操作 (Add)

- 乘法操作 (Mult)

这简直是为密封类量身定做的。

```java
// 密封接口：表达式
sealed interface Expr permits Num, Add, Mult {}

// 数字
record Num(int value) implements Expr {}

// 加法：包含左右两个表达式
record Add(Expr left, Expr right) implements Expr {}

// 乘法：包含左右两个表达式
record Mult(Expr left, Expr right) implements Expr {}

// --- 计算逻辑 ---
public int eval(Expr e) {
    return switch (e) {
        // 如果是数字，直接返回
        case Num n -> n.value();
        
        // 如果是加法，递归计算左边 + 右边
        case Add a -> eval(a.left()) + eval(a.right());
        
        // 如果是乘法，递归计算左边 * 右边
        case Mult m -> eval(m.left()) * eval(m.right());
    };
}
```
